## 1. [Security] Control channel reuses the same AES-GCM IV for every encrypted packet (key/IV reuse)

**Severity:** High

Every server→client encrypted control packet is encrypted with `seq = 0`, so the entire
control session uses a single (key, IV) pair.

**Evidence**

`src/moonlight-server/control/control.cpp:89`:

```cpp
auto encrypted = control::encrypt_packet(aes_key, 0, payload); // TODO: seq?
```

`src/moonlight-protocol/moonlight/control.hpp` — `encrypt_packet` builds a 16-byte IV whose
only non-zero byte is the 32-bit `seq` (and only its first byte is written):

```cpp
std::array<uint8_t, 16> iv_data{};
...
iv_data[0] = boost::endian::native_to_little(seq);
```

The reference implementation (Sunshine, `src/session.cpp` / `src/stream.cpp`) increments a
per-session sequence number for every encrypted control message:

```cpp
auto seq = session->control.seq++;
```

**Impact**

AES-GCM with a repeated (key, IV) pair leaks the GHASH subkey H and the keystream prefix:
the XOR of two ciphertexts equals the XOR of the plaintexts, and with H an attacker can
forge authenticated control packets. The control channel carries the video/audio AES-GCM
session keys and all input commands, so a network-position attacker (same LAN / compromised
adjacent host) can recover and forge control traffic.

**Suggested fix**

Keep a per-connection `std::atomic<std::uint32_t> seq` on the control session and pass
`seq++` into `encrypt_packet` (matching Sunshine). The client already expects a 32-bit
counter in IV byte 0; wire format does not change.

## 2. [DoS] Unauthenticated `/unpair` HTTP endpoint crashes the server with a missing header or unknown client

**Severity:** High

**Evidence**

`src/moonlight-server/rest/servers.cpp:58-68`:

```cpp
server->resource["^/unpair$"]["GET"] = [&state](auto resp, auto req) {
  auto headers = req->parse_query_string();
  auto client_ip = get_client_ip<SimpleWeb::HTTP>(req);
  auto client_id = get_header(headers, "uniqueid");
  ...
  auto cache_key = client_id.value() + "@" + client_ip;      // throws if header missing
  auto client = state->pairing_cache->load()->at(cache_key); // throws if key missing
  state::unpair(state->config, state::PairedClient{.client_cert = client.client_cert});
```

- `client_id` is a `std::optional`; `.value()` throws `std::bad_optional_access` when the
  `uniqueid` query/header is absent.
- `at(cache_key)` throws `std::out_of_range` for any unknown client.
- The exception propagates out of the Simple-Web-Server handler with no try/catch →
  `std::terminate` → the whole wolf process dies.

The plain-HTTP server (port 47984) is unauthenticated and bound to `0.0.0.0`.

**Repro**

```bash
curl "http://<wolf-host>:47984/unpair"
```

→ wolf terminates.

**Suggested fix**

Validate `client_id` and the cache lookup, return `400` on failure instead of throwing
(same pattern as `/pin/`, which wraps the lookup in try/catch).

## 3. [Crash] wolf crashes at startup when no PulseAudio server is available (broken "audio disabled" path)

**Severity:** High

**Evidence**

`src/moonlight-server/wolf.cpp` — `setup_audio_server()` returns
`std::optional<AudioServer>` and explicitly supports the no-audio case:

```cpp
logs::log(logs::warning, "Failed to connect to any PulseAudio server, audio will not be available!");
return std::nullopt;
```

…but the result is dereferenced unconditionally:

```cpp
auto pulse_router_state = std::make_shared<audio::PulseAudioRouterState>(audio_server->server);
```

`std::nullopt` → dereferencing an empty optional → UB/crash at startup on any host without a
usable PulseAudio (both the embedded PA socket and the `WolfPulseAudio` sidecar failing).

Related, `src/moonlight-server/sessions/common.cpp:24-33` — with no audio server,
`audio_server_name` is `""`, so the runner still gets:

```cpp
full_env.set("PULSE_SERVER", audio_server_name);           // empty
mounted_paths.push_back({audio_server_on_host, audio_server_name}); // mount destination ""
```

An empty mount destination is rejected by the Docker API, so even if the startup crash were
fixed, session containers would fail to create.

**Impact**

The documented "audio will not be available" degradation path crashes the server (or, if
survived, breaks every session).

**Suggested fix**

- Guard `PulseAudioRouterState` creation on `audio_server.has_value()`.
- In the runners, only set `PULSE_SERVER` / add the runtime-dir mount when a server name
  exists.

## 4. [Protocol] RTSP multi-chunk message assembly duplicates/truncates data

**Severity:** Medium-High

**Evidence**

`src/moonlight-server/rtsp/net.hpp` — `receive_message` accumulates partial messages in
`prev_read_`, but `streambuf_` is never consumed after the read:

```cpp
boost::asio::async_read(socket_, streambuf_, ...) {
  ...
  std::string raw_msg((std::istreambuf_iterator<char>(streambuf_)), std::istreambuf_iterator<char>());
  auto full_raw_msg = self->prev_read_ + raw_msg;
  auto total_bytes_transferred = self->prev_read_bytes_ + bytes_transferred;
  full_raw_msg.resize(total_bytes_transferred);
```

On the second chunk, `raw_msg` contains **both** chunk 1 and chunk 2 (the streambuf still
holds chunk 1), so `full_raw_msg = chunk1 + chunk1 + chunk2` and `resize(chunk1+chunk2)`
keeps `chunk1 + chunk1` — the first N bytes are duplicated and the last N bytes of the real
message are lost.

Secondary: `std::stoi(total_length_str)` (line 175) throws on a malformed `Content-length`
inside the async lambda; the exception propagates out of `io_context::run()`.

**Impact**

Any RTSP request whose body (typically `ANNOUNCE` with SDP) arrives split across two TCP
reads is corrupted → session setup fails. Small messages in one segment work, which is why
this is intermittent.

**Suggested fix**

Consume the streambuf after reading (`streambuf_.consume(streambuf_.size())`), or track the
unprocessed tail explicitly instead of re-reading the whole buffer. Wrap the Content-length
parse in validation.

## 5. [UB] `control::get_ip` reads uninitialized memory on every ENet event

**Severity:** Medium-High

**Evidence**

`src/moonlight-server/control/control.cpp`:

```cpp
auto ip_addr = reinterpret_cast<sockaddr *>(&event.peer->address.address);
...
if (ip_addr->sa_family == AF_INET) { ... }
else if (ip_addr->sa_family == AF_INET6) { ... }
```

`ENetAddress::address` is a union of `in_addr`/`in6_addr` (raw IP bytes), **not** a
`sockaddr`. Casting it to `sockaddr*` and reading `sa_family` interprets the first two bytes
of the IP address as the family — for `192.168.1.5` that is `0xA8C0`, which matches neither
`AF_INET` (2) nor `AF_INET6` (10). Both branches are skipped, so `port` and `data` stay
**uninitialized**, and `std::string{data}` then reads an indeterminate-length stack buffer
(UB) on every ENet event.

Consequence: the IP-based fallback in `get_current_session` (matching sessions by
`client_ip`) can never match, since the IP string is garbage. Primary matching uses the
secret payload, which is why sessions generally still work.

**Suggested fix**

Use the real fields: `event.peer->address.port` and `inet_ntop(AF_INET/AF_INET6,
&event.peer->address.address, ...)` (the union already tells you the family via
`event.peer->address` handling in enet).

## 6. [Crash] Control channel: ENet host creation failure returns a null host; `utf8_text` underflows on short packets

**Severity:** Medium

**Evidence**

1. `src/moonlight-server/control/control.cpp` — `create_host()`: when `enet_host_create()`
   returns `nullptr` (e.g. control port already in use), the error is logged but the function
   still returns `{nullptr, free_host}`; the service loop then calls
   `enet_host_service(nullptr, ...)` → segfault.

2. `src/moonlight-server/control/input_handler.cpp:443` — `utf8_text()`:

   ```cpp
   auto size = boost::endian::big_to_native(pkt.data_size) - sizeof(pkt.packet_type) - 2;
   ```

   If a `UTF8_TEXT_PACKET` has `data_size < 3` (attacker/paired-client controlled), the
   unsigned subtraction underflows and `pkt.text + size` points far out of bounds;
   `to_utf` reads OOB → crash/UB.

**Suggested fix**

- Return an error/`nullopt` from `create_host` and fail the control server startup cleanly.
- Reject `UTF8_TEXT_PACKET`s with `data_size < 3` (and bounds-check `text` against the
  received packet length).

## 7. [Robustness] Wolf API (unix socket) server: unhandled exceptions terminate the process; data race on `state_->sockets`

**Severity:** Medium

**Evidence**

1. `src/moonlight-server/api/http_server.hpp:60`:

   ```cpp
   boost::asio::post(pool_, [handler, boxed_request, socket]() { handler(*boxed_request, socket); });
   ```

   No try/catch around the handler. Endpoints throw on malformed input, e.g.
   `src/moonlight-server/api/endpoints.cpp`:
   - `payload.client_id.value()` (lines 70, 559) — `bad_optional_access` if `client_id` is
     missing from the JSON body;
   - `std::stoul(start_req.value().session_id)` (lines 303, 334, 356, 379, 530) —
     `std::invalid_argument` for a non-numeric session id.

   Any of these → exception in the thread-pool task → `std::terminate` → the entire wolf
   process dies.

2. `src/moonlight-server/api/unix_socket_server.cpp:348-349`:

   ```cpp
   void UnixSocketServer::sse_broadcast(const std::string &payload) {
     for (auto &socket : state_->sockets) {
   ```

   `state_->sockets` is a plain `std::vector` mutated (push_back / erase in
   `cleanup_sockets`) on the io_context thread while `sse_broadcast` iterates it from
   (a) the SSE keepalive timer, (b) event-bus handler threads, and (c) a **detached thread**
   in `endpoint_DockerPullImage`. Concurrent reallocation during iteration is UB → crash.

**Suggested fix**

- Wrap the handler invocation in try/catch and return a 500 on exception.
- Protect `state_->sockets` with a mutex (or swap-to-local under lock before iterating).

## 8. [Protocol] HTTPS REST endpoints: `resume()` double-writes the response; `.value()` on optional headers crashes the server

**Severity:** Medium

**Evidence**

`src/moonlight-server/rest/endpoints.hpp`:

1. `resume()` (line 442): the success path calls
   `send_xml(..., success_ok, xml)` and then — unconditionally — `server_error(response)`,
   writing a second (400) response to the same connection. The second write corrupts/drops
   the first; clients resuming a session get an ambiguous response.

2. `create_run_session()` (lines 391-392):

   ```cpp
   get_header(headers, "rikey").value(),
   get_header(headers, "rikeyid").value())
   ```

   and `launch()` (line 416) `get_header(headers, "appid").value()` — missing header →
   `bad_optional_access` → uncaught in the SimpleWeb handler → `std::terminate`.

3. `serverinfo()` (line 65): `std::stoi(stream_session->app->base.id)` — a non-numeric
   (user-configured) app id throws on **every** serverinfo poll while that session runs.

4. `launch()` (line 376): the `mode` header is split on `'x'` and each part `std::stoi`'d;
   a malformed `mode` (wrong arity / non-numeric) throws `out_of_range`/`invalid_argument`
   → terminate.

**Suggested fix**

Use `value_or` / validated parsing with a 400 response (the pattern already used in
`launch()` for the app-not-found case), and remove the trailing `server_error` from
`resume()`'s success path.

## 9. [Config] `config.toml`: re-pairing accumulates duplicate entries; `default_source.replace(0, 12, ...)` corrupts custom pipelines

**Severity:** Medium

**Evidence**

`src/moonlight-server/state/configTOML.cpp`:

1. `pair()`: the in-memory `pairing` atom is deduplicated by `client_cert` (the #211 fix),
   but the TOML write path unconditionally appends:

   ```cpp
   config->pairing.value()->push_back(pairing);
   ```

   Re-pairing the same client (e.g. re-pair after unpair+pair, or a race) appends a second
   entry for the same cert to `config.toml`. Duplicates grow the file forever and make the
   file drift from the in-memory state.

2. `load_or_default()` (lines 257, 262):

   ```cpp
   default_gst_video_settings.default_source.replace(0, 12, "interpipesrc name=interpipesrc_{}_video");
   default_gst_audio_settings.default_source.replace(0, 12, "interpipesrc name=interpipesrc_{}_audio");
   ```

   If a user customized `default_source` to anything not starting with the expected
   `interpipesrc` prefix, the first 12 characters are blindly replaced, producing an
   invalid GStreamer pipeline string that breaks streaming for that app.

**Suggested fix**

- Deduplicate by `client_cert` before appending to the TOML list.
- Only do the replace when `default_source` actually contains the expected
  `name=interpipesrc` source (or use a find/replace of the exact token).

## 10. [Crypto] OpenSSL helpers: unbounded VLAs on the stack, non-throwing error handling, null key returned on PEM failure

**Severity:** Medium

**Evidence**

`src/moonlight-protocol/crypto/src/aes.hpp`:

```cpp
unsigned char ciphertext[c_len];   // c_len = len + AES_BLOCK_SIZE, line 47 & 89
unsigned char plaintext[cipher_length]; // line 67 & 117
```

These are VLAs (GNU extension, not standard C++) sized directly from the input length.
`encrypt_symmetric`/`decrypt_symmetric` are used on the pairing path where the input size
is network-controlled → a large payload causes a large stack allocation → stack overflow →
crash (remote DoS via the HTTPS pairing endpoint). A zero-length input creates a
zero-length array (invalid).

`src/moonlight-protocol/crypto/src/utils.cpp` — `handle_openssl_error` only prints to
stderr and returns; it does **not** throw or abort. Consequences:

- On `EVP_CipherInit` failure, `encrypt_symmetric` proceeds and returns
  `uc_to_str(ciphertext, len)` — **uninitialized stack bytes** — as the "ciphertext"
  (silent corruption, no error surfaced to the caller).
- `src/moonlight-protocol/crypto/src/sign.hpp` — `create_key` returns a
  `unique_ptr<EVP_PKEY, ...>` wrapping `nullptr` when PEM loading fails; callers pass the
  null key straight into `EVP_DigestSignInit` → crash.

**Suggested fix**

- Use `std::vector<uint8_t>` (or a size-capped stack buffer) instead of VLAs.
- Make `handle_openssl_error` throw (or return an error code that callers check); return
  `nullopt`/empty results on failure instead of garbage.

## 11. [Leak] `wait_for_ping` has no timeout: a client that never pings leaks a thread and an event-bus handler forever

**Severity:** Low-Medium

**Evidence**

`src/moonlight-server/sessions/moonlight.cpp:28-41`:

```cpp
auto handler = ev_bus->register_handler<immer::box<RTPPingType>>(...);
auto ping_ev = ping_future.get();   // no timeout
handler.unregister();
```

`wait_for_ping` is called from a detached thread per session. If the RTP ping never arrives
(client crashes/closes the connection between the RTSP handshake and the first ping, or the
UDP is firewalled), `ping_future.get()` blocks forever: the thread leaks and — more
importantly — the RTP-ping event-bus handler (which captures a full `StreamSession` copy,
including the wayland display handle) is never unregistered, so it stays armed and keeps
that state alive indefinitely.

**Suggested fix**

Wait with a timeout (e.g. `ping_future.wait_for(...)` in a loop, or a
`boost::asio::deadline_timer`); on timeout, unregister the handler and tear the session
down (fire `StopStreamEvent`).

## 12. [Misc] Smaller issues (candidates for a single cleanup PR)

**Severity:** Low

- **mDNS advertises a hardcoded port** — `src/moonlight-server/wolf.cpp:231`:
  `mdns.setServicePort(state::HTTP_PORT)` uses the compile-time constant (47989) instead of
  `get_port(state::HTTP_PORT)`, so a `WOLF_HTTP_PORT` override is not reflected in mDNS
  discovery.
- **`get_port` crashes on non-numeric env vars** — `src/moonlight-server/state/data-structures.hpp:47-55`:
  `std::stoi(utils::get_env("WOLF_HTTPS_PORT"))` etc. throw at startup (inside a detached
  server thread → terminate).
- **`send_http` always reports "OK"** — `src/moonlight-server/api/unix_socket_server.cpp`:
  the status text is hardcoded `"OK"` even for 404/500 responses (cosmetic).
- **PulseAudio `disconnect()` leaves the ready-promise unfulfilled** —
  `src/core/src/platforms/linux/pulseaudio/pulse.cpp`: `disconnect()` recreates
  `on_ready` but the state callback never sets the new promise (UNCONNECTED does nothing),
  so `connected()` after a disconnect blocks forever. Also `create_virtual_sink` silently
  returns a `VSink` that is never created when the PA context isn't READY (the queued op is
  skipped), leaving `sink_idx` unset — the audio producer then starts a `pulsesrc` for a
  non-existent monitor and the session runs without audio.
- **CUDA device index mapping heuristic** — `src/gst-video-context/gst-video-context.cpp`:
  `getCudaDeviceIndexFromPciBusId` maps PCI bus ID → CUDA index by sorting
  `/proc/driver/nvidia/gpus/*`; that ordering is not guaranteed to match CUDA's device
  order, and `create_cuda_context` falls back to device 0 silently when the mapping fails —
  on multi-GPU hosts the CUDA context can be created on the wrong GPU. Prefer
  `cuDeviceGetPCIBusId`.
- **Dead code**:
  - `src/moonlight-server/rest/servers.cpp`: `pair_handler.unregister()` after the blocking
    `server->start()` — unreachable.
  - `src/moonlight-server/runners/docker.cpp`: `use_fake_udev = !fake_udev_cli_path.empty()
    || std::filesystem::exists(fake_udev_cli_path)` — the `exists()` branch is unreachable
    (if the path is empty, `exists("")` is false).
- **mDNS logger underflow** — `wolf.cpp`: `msg.substr(0, msg.size() - 1)` on an empty log
  message throws `std::out_of_range`.

## False positives checked and dismissed (do NOT file)

- FEC multi-block header layout (`video.hpp`) — matches Sunshine
  `(blockIndex << 4) | ((fec_blocks_needed - 1) << 6)` for 3 blocks.
- `MOUSE_MOVE_ABS_PACKET` 16-bit x/y/width/height — matches Sunshine's `mouse_move_abs_t`
  (the 8K limit is in the real GFE protocol).
- Event-bus handler "leaks" in the docker runner — `EventBusHandlers` is RAII and
  auto-unregisters on scope exit; handlers live exactly as long as `run()` blocks.
- GStreamer bus signal handlers in `run_pipeline`/`start_video_producer` — the raw-pointer
  user data (`bus_data_ptr.get()`) outlives the bus: the bus dies with the pipeline, which
  is destroyed inside `run_pipeline` before the owning shared_ptrs go out of scope.
- Audio plugin `set_property` — handles all four properties correctly.
- `CONTROLLER_MULTI_PACKET` layout — supported by existing captured-packet tests.
